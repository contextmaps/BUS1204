Writing the Governance Section for an Agent That Acts
Duration: 75 minutes · Platform: Hokie AI · Submission: The regular Hokie AI thread, holding the governance drafting, the retest audit and the reflection, exported as a .zip and uploaded to Canvas before leaving class · Lecture Mode: consolidation
Learning Objectives

By the end of this lecture, students will be able to:

  1. Name the four governance principles, Authority, Approval, Accountability and Audit, and the kind of rule each one produces for an agent that acts.
  2. Turn the actions in an audit of an agent into rules, and file each rule under the principle it serves.
  3. Write a GOVERNANCE section with Hokie AI and install it in an agent, together with a tool that sends a request to a person for approval.
  4. Probe an agent under each principle and read from Execution Details which rules held, which slipped and which went too far.
  5. Decide where a rule should live: in the instructions, in the tool's schema or in the system that receives the call.

INTRODUCTION
📋 Note for Students

On Tuesday your Half Note Studios agent booked whatever the tools allowed. Many of you asked for a studio for several days in a row, or for a session on a date already past, and the agents booked them.

Today you write the rules. You draft a GOVERNANCE section for your own agent with Hokie AI, install it, give the agent a way to ask the studio manager, and test it with a probe for each principle.

On Tuesday your agent booked whatever the tools allowed. The card shows the kinds of request that came back booked.

Governance is the set of rules for how an agent operates inside a business. Each of Tuesday's four questions produces its own kind of rule. Learn the four names, because every rule you write today belongs under one of them.

Approval needs a way to reach a person. Today your agent gets a third tool, request_approval, which sends the request to the studio manager and books nothing. Its response says pending and gives an approval ID, so the request leaves a record you can audit.

A rule can live in three places. Today your rules live in the instructions, which the agent reads and can still get wrong. A limit in the tool's schema is checked before the call is made. The studio's own booking system receives the call, and it is the only place that can say no every time.

Section 4 of 5
DISCUSSION

Turn to the person beside you. Tell your partner one probe and what your agent did with it AND read the audit line that shows it AND name the principle behind the rule. Four minutes, both directions.

💬 Discussion

Take these into the reflection:

  • Which of your rules held on the first try, and which principle does it serve?
  • If a rule slipped, it lives in the instructions. Would that rule be safer in the schema or in the studio's own system, and what would it cost to move it?
  • Which rule do you trust least after reading your audit, and what in the audit makes you doubt it?
